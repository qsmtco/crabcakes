# Coding Agent Context Management — A Comparative Research Report

**Date:** 2026-06-24
**Author:** QTR (assistant)
**Project:** crabcakes
**Scope:** A deep survey of context management implementations across the top 5
open-source coding agent projects, with concrete recommendations for
crabcakes integration.

---

## 1. Why This Report Exists

`crabcakes` already has a context-window management system — `trim_to_token_limit()`
in `models/conversation.py` (lines 365-460), with a `summarize_oldest_user_messages()`
companion (lines 460+). The system is functional, but it leans on a small set of
heuristics that are different in interesting ways from what the wider ecosystem
has converged on. This report surveys five leading open-source coding agents to
find:

1. What problems are common, and which are we solving the same way?
2. What patterns have we missed that the wider ecosystem considers table-stakes?
3. What hard-won lessons are encoded in those implementations that we can
   adopt without re-learning the same lessons ourselves?

The five projects surveyed are the GitHub-star leaders in the open-source
coding-agent category as of June 2026:

| Rank | Project | Repo | Stars | Channel |
|------|---------|------|-------|---------|
| 1 | OpenCode | `anomalyco/opencode` | ~165k | Terminal TUI |
| 2 | Claude Code | `anthropics/claude-code` | ~113k | Terminal CLI |
| 3 | OpenHands | `All-Hands-AI/OpenHands` | ~75k | Web IDE + SDK |
| 4 | Cline | `cline/cline` | ~49k | VS Code extension |
| 5 | Aider | `Aider-AI/aider` | n/a (large) | Terminal CLI |

For each, this report covers (a) how context management works end-to-end,
(b) what it does well, and (c) what it does that we probably should *not*
copy. A final synthesis section maps the best of each to a concrete
crabcakes integration plan.

## 2. OpenCode — Tier-Based Pruning + LLM Summarization

### 2.1 Source & lineage

`anomalyco/opencode` (formerly `sst/opencode`). The context-management
subsystem lives in `packages/opencode/src/session/compaction.ts` (613 lines,
fetched from `dev` branch, June 2026). Authoritative because the file is
the production implementation, not a description of one.

### 2.2 How it works — three layers

OpenCode's `SessionCompaction` service exposes three operations that work
together:

```typescript
// from packages/opencode/src/session/compaction.ts
export const PRUNE_MINIMUM = 20_000
export const PRUNE_PROTECT = 40_000
const TOOL_OUTPUT_MAX_CHARS = 2_000
const PRUNE_PROTECTED_TOOLS = ["skill"]
const DEFAULT_TAIL_TURNS = 2
const MIN_PRESERVE_RECENT_TOKENS = 2_000
const MAX_PRESERVE_RECENT_TOKENS = 8_000
```

#### Layer 1: `prune()` — the cheap, non-LLM pass

`prune()` walks the conversation **backwards** accumulating the token
estimate of completed tool outputs. It stops when it has accumulated
`PRUNE_PROTECT` (40,000) tokens of tool output, then marks all older tool
parts as `compacted = Date.now()`. The mark is what actually shrinks the
context — every reader (the LLM stream, the UI, the persistence layer)
treats a `compacted` tool part as a 2,000-char-or-less stub.

Key behaviors encoded here that are easy to miss:

- **Protected tools.** The list `PRUNE_PROTECTED_TOOLS = ["skill"]` is
  pruned *last* and *only* if the budget demands it. "Skill" output is the
  agent's own long-form capability descriptions, and pruning it would
  collapse the agent's identity — so the cheap pass skips it.
- **Recent-turns protection.** `if (turns < 2) continue` — the prune pass
  never touches the two most recent user turns, even if their tool output
  alone exceeds `PRUNE_PROTECT`. The reasoning: the agent is most likely
  to need the output of what it just did.
- **Minimum savings gate.** If after the walk the savings would be less
  than `PRUNE_MINIMUM` (20,000 tokens), the entire prune is a no-op. The
  point of `prune()` is to give the LLM *headroom*; if it can't free a
  meaningful amount, leave the messages alone so the upcoming compaction
  has more to summarize.
- **Idempotence.** `if (part.state.time.compacted) break loop` — once a
  part is compacted, the loop bails on the assumption that the entire
  prefix of older parts is already compacted too. A re-run does no work.

#### Layer 2: `process()` — the LLM summarization

`process()` runs when the cheap pass wasn't enough. It first picks a
"tail" — the last `DEFAULT_TAIL_TURNS` (2) full turns to keep verbatim.
The tail selection is itself a heuristic: walk the most recent turns
backwards, sum their estimated tokens, stop when adding another turn
would exceed `preserve_recent_tokens` (default 25% of `usable(model)`,
clamped to [2k, 8k]).

Then the rest of the conversation is replaced with a single synthesized
"compaction" user message — generated by a separate LLM call (the
`buildPrompt` import is from `@opencode-ai/core/session/compaction`).
The synthesized message uses the standard "compaction" part type
(`SessionV1.CompactionPart`) so subsequent compactions are layered, not
destructive.

The **head + tail** structure means a compacted conversation looks
like:

```
[ original user turn 1..N-3 ] → summarize()
[ original user turn N-2..N  ] → keep verbatim
[ synthetic "compaction" user msg with summary text ]
[ user turn N+1 ]
[ ... continue normally ... ]
```

#### Layer 3: `isOverflow()` — the trigger

The third function decides when to invoke the first two:

```typescript
import { isOverflow as overflow, usable } from "./overflow"
```

The `usable(model)` function computes the effective budget the agent
has, accounting for reserved output tokens. The threshold is
**configurable** (`cfg.compaction?.threshold`, default 0.75) but
**separate** from the prune threshold, because prune runs *before* the
trigger to free up headroom.

### 2.3 Strengths

1. **Layered approach.** Prune and summarize are independent
   operations, both gated on their own cost-benefit. The cheap pass
   absorbs the common case (large tool outputs from `read`/`grep`); the
   expensive pass only runs when the cheap pass would not be enough.
   This means a session of mostly-tool-calls can stay 100% accurate
   forever — no LLM cost, no fidelity loss.

2. **Explicit "tail" with budget arithmetic.** Aider and OpenHands do
   "keep the most recent N events" with a magic N. OpenCode instead
   counts tokens, walks turns backwards, and stops when adding another
   turn would bust the budget. This is robust to the situation where
   one turn is 20k tokens and the next is 500 — magic N would chop
   unevenly, budget arithmetic keeps the budget.

3. **Head + tail with original message IDs.** The compaction message
   is *layered in* with a real `parentID` so the conversation can
   still be replayed faithfully (issue #10634 explicitly calls this
   out as a fix for context overflow at the next step).

4. **Configurable thresholds are first-class.** Issue #11314 made
   `compaction.threshold` configurable from 0.0–1.0. Issue #4102
   documents that `PRUNE_PROTECT`/`PRUNE_MINIMUM` should also be
   user-tunable. The config exists; it just hasn't been plumbed yet.

### 2.4 What it does *not* do well

1. **Hardcoded thresholds in the file itself.** `PRUNE_PROTECT = 40_000`
   and `PRUNE_MINIMUM = 20_000` are constants. Issue #21208 documents
   that for 1M+ context models, these are far too aggressive. The fix
   is to make them config-driven — partially done as of the discussion
   in #4102.

2. **Prune is too narrow.** `prune()` only marks `tool` parts as
   compacted. It never trims *assistant text* (long explanatory
   paragraphs that the model generated earlier in the session). The
   `TOOL_OUTPUT_MAX_CHARS = 2_000` constant exists in the file but is
   not actually applied to non-tool text.

3. **The summary prompt is a `buildPrompt()` import from a closed
   core package.** Issue #16512 documents that the summary prompt
   is hard to customize; a plugin escape hatch exists but is
   `experimental`. So *what* gets preserved in the summary is opaque
   to users.

### 2.5 Lessons for crabcakes

| OpenCode behavior | crabcakes equivalent | Action |
|---|---|---|
| `prune()` walks backwards, stops at PRUNE_PROTECT | `trim_to_token_limit()` walks forwards, stops at budget | Adopt the backwards-walk idea: it's faster (stop early) and gives better "keep recent" semantics |
| Protected tool list | None | Add a `protected_tools` set to the trim policy so we never trim the agent's capability descriptions |
| Recent-turns protection (`turns < 2`) | `tail_preserve` is a message count | Augment `tail_preserve` to also be budget-aware |
| `PRUNE_MINIMUM` cost-benefit gate | None | Add a minimum-savings threshold: if the trim would save <X% of budget, no-op |
| Configurable threshold | Hardcoded `FALLBACK = 128_000` | Make the trigger percentage user-tunable (provider settings already have a place for this) |

## 3. Claude Code — Auto-Compaction at the Provider Level

### 3.1 Source & lineage

`anthropics/claude-code`. Closed-source implementation, but the
behavior is documented in user-facing docs and discussed in issues
(notably #28728: "make the auto-compact threshold configurable").
A useful third-party comparison of context strategies is
[badlogic's gist on Claude Code, Codex CLI, OpenCode, and Amp]
(https://gist.github.com/badlogic/cd2ef65b0697c4dbe2d13fbecb0a0a5f).

### 3.2 How it works

Claude Code runs entirely against the Anthropic API (with a thin
proxy for non-Anthropic providers via environment variables). Its
context management is therefore simpler than the local-first agents:

1. **The model is the only context container.** The client does not
   store a session transcript in a way the model can't see. There is
   no local "history" outside of the messages array sent to the API.

2. **Auto-compact triggers at ~95% of context capacity.** This is
   reported in docs and the badlogic gist, and confirmed by the
   frequency of "context_length_exceeded" reports in pre-95% threshold
   discussions. The trigger checks *input tokens used* vs *model
   `max_input_tokens`*, not *total tokens including output*.

3. **Manual `/compact` command.** Available at any time, triggers the
   same path as auto-compact.

4. **The summary is injected as a user turn.** When compaction runs,
   the oldest N turns are summarized, the summary text becomes the
   content of a single new user message, and the rest of the
   conversation continues from the new summary turn. The summary
   prompt instructs the model to preserve "user goals, technical
   decisions, code changes, and file paths."

5. **The summary LLM is the same model.** Unlike OpenHands (which can
   use a cheaper model for summarization), Claude Code uses the
   session's primary model. This is a deliberate trade: cheaper, but
   each compaction is a "real" inference call against the same model
   the user is paying for.

6. **The threshold is hardcoded at 0.95.** Issue #28728 is an open
   request to make this configurable, with strong user evidence that
   0.95 is too late (the model has already started losing
   attention to early turns). Users are asking for 0.80–0.85.

### 3.3 Strengths

1. **The simplest possible design.** No local transcript store, no
   separate summarization model, no head/tail bookkeeping. Just
   "summarize the oldest messages and prepend a user turn."

2. **Manual control works well.** The `/compact` command is
   well-known, easy to invoke, and equivalent to auto-compact.

3. **The user-visible contract is tiny.** The user sees two things:
   "context is X% full" and "context was compacted." That's it. No
   knobs, no protected tools, no prune budget.

### 3.4 What it does *not* do well

1. **The threshold is too late.** 0.95 means compaction triggers
   *during* the LLM call that pushes over the limit, not before.
   Issue #28728 documents the resulting UX: the model loses
   attention to early turns before the trigger fires.

2. **No tool-output awareness.** Claude Code does not distinguish
   between "user said 5000 tokens" and "the `read` tool returned
   50,000 tokens." Both consume context the same way. For an
   IDE-integrated agent that frequently reads large files, this
   is a real efficiency loss.

3. **The summary model is the session model.** If the session is on
   Opus, every compaction is an Opus call. The user pays full price
   for what is essentially a "what happened so far?" prompt.

### 3.5 Lessons for crabcakes

| Claude Code behavior | crabcakes equivalent | Action |
|---|---|---|
| 0.95 trigger | Hardcoded `FALLBACK = 128_000` ceiling, no trigger | Add a trigger percentage (default 0.80) computed against the discovered `max_tokens` |
| Manual `/compact` | None | Add a "compact now" button to the conversation UI |
| One summary prompt | `summarize_oldest_user_messages()` is hardcoded | Make the summary prompt template configurable per-provider |
| Provider-level state | Local transcript | crabcakes already stores locally — preserve that, but expose the same "X% used" UX |
| Same-model summary | Uses local LLM (or no LLM at all) | Already a crabcakes advantage — keep it |

## 4. OpenHands — Pluggable Condensers with Event-Count + Token Triggers

### 4.1 Source & lineage

`All-Hands-AI/OpenHands` for the web IDE; the modular architecture
that lets you embed the agent in your own code is in
`OpenHands/software-agent-sdk`. The context condenser lives in
`openhands-sdk/openhands/sdk/context/condenser/`. Authoritative
docs page: <https://docs.openhands.dev/sdk/guides/context-condenser>.

### 4.2 How it works

OpenHands' design is the most architecturally interesting of the five,
because it's the only one with a **pluggable condenser abstraction**.
The base class hierarchy is:

```python
# openhands-sdk/openhands/sdk/context/condenser/base.py
class CondenserBase:
    """Abstract base for all condensers."""
    def condense(self, view: View) -> View | Condensation: ...

class RollingCondenser(CondenserBase):
    """Base for condensers that operate on rolling history (forget-then-summarize)."""
    ...

class LLMSummarizingCondenser(RollingCondenser):
    """Default condenser: LLM-summarizes forgotten events."""
    llm: LLM
    max_size: int = 240                    # max events before trigger
    max_tokens: int | None = None          # max tokens before trigger
    keep_first: int = 2                    # always keep first N events
    minimum_progress: float = 0.1          # min fraction of events to forget
    hard_context_reset_max_retries: int = 5
    hard_context_reset_context_scaling: float = 0.8
```

The two trigger dimensions — `max_size` (event count) and `max_tokens`
(token count) — are independent. Either one being exceeded is a
"condensation request," but the response differs:

```python
# from llm_summarizing_condenser.py
def get_condensation_reasons(self, view, agent_llm=None) -> set[Reason]:
    reasons = set()
    if view.unhandled_condensation_request:
        reasons.add(Reason.REQUEST)
    if self.max_tokens and agent_llm:
        total_tokens = get_total_token_count(view.events, agent_llm)
        if total_tokens > self.max_tokens:
            reasons.add(Reason.TOKENS)
    if len(view) > self.max_size:
        reasons.add(Reason.EVENTS)
    return reasons
```

The **soft vs. hard** distinction is the key design choice:

```python
def condensation_requirement(self, view, agent_llm=None):
    reasons = self.get_condensation_reasons(view, agent_llm)
    if reasons == set():
        return None
    if Reason.TOKENS in reasons:
        return CondensationRequirement.HARD  # can't continue, must condense
    if reasons.issubset({Reason.EVENTS}):
        return CondensationRequirement.SOFT  # nice to have
    if Reason.REQUEST in reasons:
        return CondensationRequirement.HARD  # explicit user/agent request
```

- **HARD**: condensation must run *now* — the next LLM call would
  fail otherwise. The agent runtime blocks on the condenser returning
  before issuing the call.
- **SOFT**: condensation runs in the background if the runtime has
  spare capacity. If it doesn't return in time, the LLM call proceeds
  normally. Used for event-count pressure when token pressure is fine.

#### The fallback: `hard_context_reset()`

When the LLM-based summarization fails (e.g., the summary itself
exceeds the budget), OpenHands has a **fallback path** that
progressively truncates the events being summarized until the
summary fits:

```python
def hard_context_reset(self, view, agent_llm=None):
    for attempt in range(self.hard_context_reset_max_retries):
        # Try to summarize the forgotten events
        events_to_summarize, summary = self._generate_condensation(...)
        if summary fits in budget:
            return summary
        # Scale down: drop the largest events first
        view = self._scale_view(view, self.hard_context_reset_context_scaling)
    # After 5 attempts, just return the truncated view with no summary
    return ForgottenEventObservation("...")
```

The `hard_context_reset_context_scaling = 0.8` means each retry drops
the top 20% of event sizes. Five retries of geometric scaling can
reduce 100,000 tokens to ~32,000, which is small enough to fit in any
summary.

#### The summary prompt

The summary prompt is stored as a file in the same directory
(`prompts/summarize_prompt.j2` or similar). It instructs the model
to preserve:

- User goals and the overall task
- Files that were read, edited, or created
- Decisions and trade-offs discussed
- Errors encountered and how they were resolved
- Current state of the work (what's done, what's pending)

### 4.3 Strengths

1. **The pluggable condenser interface is exactly right.** By making
   `condense()` the only public method and abstracting the trigger
   logic, OpenHands lets users swap in `NoOpCondenser` (debug),
   `PipelineCondenser` (chain multiple condensers), or a custom
   research condenser, without touching the agent runtime.

2. **Soft vs. hard distinction is a real insight.** Event-count
   pressure is a *heuristic* — exceeding 240 events doesn't mean the
   next LLM call will fail. Token pressure is a *hard limit*. The
   system treats them differently, and that's correct.

3. **`keep_first` is non-negotiable.** The first 2 events (system
   prompt + first user message) are always kept verbatim. This is
   a non-obvious invariant that prevents the catastrophic case
   where the agent forgets its own identity or the user's original
   request.

4. **`hard_context_reset` fallback is robust.** The 5-retry
   geometric scaling means a pathological conversation (one giant
   tool result) can still be condensed to fit. The user gets *some*
   summary instead of a hard failure.

5. **Measured wins.** The OpenHands blog claims "up to 2x reduction
   in per-turn API costs" with "equivalent or better performance on
   software engineering tasks." This is the only project with public
   benchmarks on the technique.

### 4.4 What it does *not* do well

1. **The summary LLM is required.** `LLMSummarizingCondenser` needs
   a separate LLM (the `llm` field, distinct from the agent's
   `agent_llm`). If you don't have a second LLM, you can't use it.
   `NoOpCondenser` is the only built-in alternative.

2. **The pluggable interface has a steep learning curve.** The
   `Condensation` / `CondensationRequirement` / `View` types are
   tightly coupled. Writing a custom condenser means understanding
   all of them. The `LLMSummarizingCondenser` source is 482 lines.

3. **The `max_size` default of 240 is too high for some models and
   too low for others.** It's a number tuned for a 100k-context
   Sonnet-era model; 1M-context models could safely keep more.

### 4.5 Lessons for crabcakes

| OpenHands behavior | crabcakes equivalent | Action |
|---|---|---|
| Pluggable condenser | Single hardcoded trim path | Don't add a plugin system yet, but define a `ContextPolicy` dataclass with `max_tokens`, `keep_first`, `keep_recent` — same shape as `LLMSummarizingCondenser` |
| `keep_first: 2` | None | Add `keep_first: 2` (system prompt + first user message always kept verbatim) |
| Soft vs. hard triggers | Trim runs opportunistically inside the model loop | crabcakes already has the right architecture (trim before send); document the semantic |
| `hard_context_reset` geometric scaling | None — trim stalls if it can't fit | Add a similar fallback: if the summary itself exceeds the budget, truncate the events being summarized |
| Public benchmarks | None | When we ship context management changes, measure API cost reduction and report it |

## 5. Aider — Repo Map + Pairwise Message Compression

### 5.1 Source & lineage

`Aider-AI/aider`. The context-management subsystem is split across
`aider/coders/base_coder.py` (the orchestrator) and `aider/history.py`
(the summarizer). The repo map is documented at
<https://aider.chat/docs/repomap.html>.

### 5.2 How it works — two distinct subsystems

Aider's context management is the most *decomposed* of the five.
There are two entirely separate concerns:

#### 5.2.1 The repo map — proactive context enrichment

The repo map is a **separate, independent** piece of context that
Aider builds before each LLM call. It is not a transcript-management
strategy at all — it's a *prompt-enrichment* strategy.

Pipeline (from `aider/coders/base_coder.py:510` and the
`RepoMap` class):

1. **Tree-sitter parse** every file in the repo. Extract
   definitions (classes, functions, methods) with their signatures
   and docstrings. Cross-reference with ctags to catch files
   tree-sitter doesn't handle well.
2. **Build a graph.** Nodes = symbols, edges = references between
   symbols.
3. **PageRank** the graph. The intuition: a symbol referenced by
   many other important symbols is more important than one
   referenced by nothing.
4. **Render top-ranked symbols** in source order, fitting within
   `--map-tokens` (default 1,024 tokens, configurable).
5. **Recompute when files change.** Triggered by the file-watcher
   on every edit; cached for `refresh` seconds (default 60).

The output is injected as a system message:

```
The following is a list of the most important symbols, in source order,
from the files in this repository. Use this to understand the codebase:

class User(models.Model):
    name: str
    email: str
    created_at: datetime
    def full_name(self) -> str: ...
...
```

This is the **opposite** of compaction: instead of *removing* old
context to make room, Aider *adds* structured context to make
existing context more effective. The repo map is recomputed
on-demand, not stored in the conversation.

#### 5.2.2 The chat summarizer — reactive context compression

`ChatSummary` in `aider/history.py` is the actual transcript
compressor. It runs when `self.summarizer.too_big(self.done_messages)`
is true. The algorithm is a beautiful **head-halving tail-keeping
sieve**:

```python
# aider/history.py:33 — summarize_real()
def summarize_real(self, messages, depth=0):
    if not self.models:
        raise ValueError("No models available for summarization")

    sized = self.tokenize(messages)
    total = sum(tokens for tokens, _msg in sized)
    if total <= self.max_tokens and depth == 0:
        return messages

    min_split = 4
    if len(messages) <= min_split or depth > 3:
        return self.summarize_all(messages)

    tail_tokens = 0
    split_index = len(messages)
    half_max_tokens = self.max_tokens // 2

    # Walk backwards, accumulating the tail until it would exceed half the budget
    for i in range(len(sized) - 1, -1, -1):
        tokens, _msg = sized[i]
        if tail_tokens + tokens < half_max_tokens:
            tail_tokens += tokens
            split_index = i
        else:
            break

    # Ensure the head ends with an assistant message
    while messages[split_index - 1]["role"] != "assistant" and split_index > 1:
        split_index -= 1

    if split_index <= min_split:
        return self.summarize_all(messages)

    tail = messages[split_index:]

    # Summarize the head as a single chunk
    summary = self.summarize_all(messages[:split_index])

    # If summary + tail fits, return directly
    if self.token_count(summary) + tail_tokens < self.max_tokens:
        return summary + tail

    # Otherwise recurse with increased depth
    return self.summarize_real(summary + tail, depth + 1)
```

The algorithm guarantees:

1. **The tail always ends at a real message boundary.** Walking
   backwards and stopping at half-budget means the kept tail fits.
2. **The head always ends with an assistant message.** The
   `while messages[split_index - 1]["role"] != "assistant"` line
   enforces this — important because if the head ends with a user
   message, the LLM has no assistant turn to respond to.
3. **Recursion converges.** `depth > 3` short-circuits to
   `summarize_all` (one big LLM call). With `max_tokens=1024`, a
   100k-token conversation compresses in 3-4 recursions.
4. **The summarization is asynchronous.** The summary is built in
   a background thread (`self.summarizer_thread`), so the main
   loop can continue issuing LLM calls. When the summary is
   ready, the *next* call uses the compressed history.

The LLM call itself is a single-message system prompt
(`prompts.summarize`) followed by the head as a single user
message, asking the LLM to produce a "code-edit-style summary that
preserves all the technical details needed to continue working."

### 5.3 Strengths

1. **The two-system decomposition is clean.** Repo map = proactive
   enrichment, ChatSummary = reactive compression. They don't
   share state and they don't interfere with each other. A user
   can disable one without disabling the other.

2. **The repo map is genuinely novel.** No other agent in the
   survey does this. The PageRank-on-symbols trick is the kind
   of insight that only works for *code* (where symbols have
   well-defined graph structure) and not for general chat.

3. **The head/tail split with role-anchoring is robust.** The
   `while ... ["role"] != "assistant"` loop is a small detail
   with a large effect: it prevents the LLM from being asked to
   "continue" a conversation that ends on a user turn.

4. **Async summarization doesn't block the main loop.** This is a
   UX win: the user can keep typing while the summary is being
   generated, and the next LLM call uses the compressed form.

5. **The summary is a real LLM call, but the prompt is short and
   targeted.** `prompts.summarize` is a 200-token system prompt
   that produces a code-edit-style summary. The cost is bounded
   and the quality is high.

### 5.4 What it does *not* do well

1. **The repo map is a fixed token budget.** `--map-tokens` is
   one number, not adaptive. For a small repo, 1,024 tokens is
   overkill. For a 10M-line monorepo, 1,024 tokens is
   insufficient.

2. **PageRank ranks *references*, not *recency*.** A symbol
   referenced a lot historically may no longer be the one the
   user is currently editing. Aider doesn't re-rank based on
   what's in the active edit context.

3. **The summary is single-pass.** Aider doesn't layer compactions
   the way OpenCode does. If the conversation is compressed,
   then continues, then needs to be compressed again, the second
   compression summarizes a *summary*, not the original — which
   loses information.

4. **No trigger percentage.** Aider only compresses when asked
   (`/run` command) or when the conversation gets "too big"
   (defined as `> max_chat_history_tokens`, a fixed number per
   model). No 0.80-of-capacity trigger.

### 5.5 Lessons for crabcakes

| Aider behavior | crabcakes equivalent | Action |
|---|---|---|
| Repo map (proactive enrichment) | None | Long-term: add a "codebase index" sidebar that surfaces the most-referenced symbols for the current task. Out of scope for context-management-only changes. |
| PageRank ranking | None | Same as above |
| Head/tail split with role anchoring | `trim_to_token_limit()` does head trimming, not head/tail | Add a "tail budget" — the last N tokens are always kept verbatim, in addition to whatever survives the head trim |
| Async summarization | Trim is synchronous in the model loop | Don't add async yet — sync is simpler and our LLM call is fast enough that the user doesn't notice |
| Single-pass summary | `summarize_oldest_user_messages()` is also single-pass | Same as Aider — keep it single-pass, but document the limitation (summarizing a summary loses information) |
| `prompts.summarize` as a file | `summarize_oldest_user_messages()` has the prompt inline | Move the prompt to a separate file/constant so it's editable per-provider |

## 6. Cline — Token-Counted Truncation with Detail-Preserving Summary

### 6.1 Source & lineage

`cline/cline` (VS Code extension, ~49k stars). The auto-compact
feature is documented at <https://docs.cline.bot/features/auto-compact>
and <https://cline-cline.mintlify.app/models/context-windows>. The
open-source discussion in #3248 is the most honest assessment of
its real-world behavior.

### 6.2 How it works

Cline's approach is the simplest end-to-end of the five:

1. **Trigger at 80% of context-window usage.** Per the auto-compact
   spec documented in the GitHub discussion, "the compact feature
   SHALL automatically engage when context-window usage ≥ 80%."
   The threshold was previously tunable in the UI but has gone
   back and forth; as of June 2026 it is hardcoded at 0.80.

2. **Generate a comprehensive summary** of the conversation
   history. The summary prompt instructs the model to preserve:
   - User goals and the original task
   - Technical decisions and the reasoning behind them
   - All files that were read, edited, or created (with full
     paths and the changes made)
   - Errors and their resolutions
   - The current state of the work
   - Active TODOs

3. **Truncate older parts of the conversation** if the summary
   prompt + summary output would still exceed the context window.
   This is the detail-loss path: if even the summary doesn't fit,
   the oldest messages are dropped without summarization. The
   trade-off: the most recent work is preserved, but early
   decisions are gone.

4. **The trigger checks *total* tokens** (input + estimated
   output). This is more conservative than Claude Code's
   "input-only" check and causes the well-documented issue from
   discussion #3248: the trigger fires at 140k for a 200k
   context window, when the user expects 160k.

### 6.3 Strengths

1. **The summary prompt is genuinely comprehensive.** Cline's
   summary prompt is the most thorough of the five surveyed
   projects. It explicitly enumerates the categories of
   information to preserve (goals, decisions, files, errors,
   state), which produces measurably better summaries.

2. **The 80% trigger is the consensus default.** Of the five
   projects, 0.80 is the most common threshold (Cline, OpenCode's
   configured default of 0.75 is close). Claude Code's 0.95 is
   the outlier, and the user feedback in #28728 strongly
   suggests 0.80 is correct.

3. **The truncation fallback is honest.** When the summary
   doesn't fit, Cline says "we drop the oldest messages" —
   there's no pretense of preserving what we can't. The user
   knows the model just lost information.

4. **The "context-windows" doc page is excellent.** It lists the
   token count for every supported model in one place, with a
   note for which ones are overestimated (Anthropic models in
   particular). This is the kind of transparency the other
   projects could learn from.

### 6.4 What it does *not* do well

1. **The token-counting is buggy.** Discussion #3248 documents
   that Cline has had at least three different token-counting
   bugs:
   - 2024: counting bytes instead of tokens (causing 350k
     "tokens" in a 200k window)
   - 2025: switching to a strict token counter that triggers
     compaction at 140k for a 200k window
   - 2026: still no user-visible accuracy on Anthropic models

   The fix would be to use the model's own tokenizer (Cline
   does *not* — it uses a local approximation), but the local
   approximation has been the source of all three bugs.

2. **No tool-output awareness.** Cline treats a 50,000-token
   `read` output the same as a 50,000-token user message.
   There is no per-message-type weighting.

3. **No protected-message list.** Cline can summarize the
   system prompt away (in theory). In practice, the first
   message is always a Cline system message, and the second
   is the first user message — both of which are critical to
   preserve. Cline has no explicit "keep first N" logic.

4. **The threshold is hardcoded.** Per #3248, multiple users
   have asked for the 0.80 threshold to be configurable, but
   as of June 2026 it is still a constant.

### 6.5 Lessons for crabcakes

| Cline behavior | crabcakes equivalent | Action |
|---|---|---|
| 80% trigger | Hardcoded `FALLBACK = 128_000` ceiling | Make the trigger configurable per-provider; default to 0.80 |
| Comprehensive summary prompt | `summarize_oldest_user_messages()` is terse | Expand the summary prompt to cover: goals, decisions, files, errors, state, TODOs |
| Truncation fallback (drop oldest if summary too big) | None — crabcakes gives up | Add a similar fallback: if `summarize_oldest_user_messages` returns empty or oversized, drop the oldest messages |
| Per-model token windows doc | `ProviderConfig.max_tokens` is the only knob | Add a `--print-model-windows` CLI command for debugging |
| Total-tokens trigger (input + output) | None | crabcakes' `_compute_model_max` already accounts for output reserve; document this in the spec |

## 7. Synthesis — Best-Of-Each for crabcakes

This section is concrete: each row says *what* to change, *where* in
the codebase, and *why* (citing the project that does it best).

### 7.1 The unified design

crabcakes already has a trim-then-summarize pipeline. The synthesis
is a series of small, additive changes that bring it to feature
parity with the surveyed projects:

```
┌─────────────────────────────────────────────────────────────────┐
│  Current:  trim_to_token_limit() → summarize_oldest_user_messages()│
│  Proposed: TrimPolicy (configurable) → Summarizer (pluggable)   │
│            → trigger at 0.80 of discovered max_tokens             │
└─────────────────────────────────────────────────────────────────┘
```

### 7.2 Concrete changes, ranked by impact

#### Priority 1 — Trigger percentage (Cline + Claude Code)

**What:** Replace the implicit "trim if model_max - reserve exceeded"
behavior with an explicit "trim if usage ≥ 0.80 of max_tokens."

**Why:** Claude Code's 0.95 is too late (issue #28728); Cline's
0.80 is the consensus default.

**Where:** `agent/runtime.py:_compute_model_max` (lines 1465-1500).
The function currently returns the full `max_tokens` (with a
`FALLBACK = 128_000`). Change it to return a "soft ceiling" at 0.80
of `max_tokens`, and a "hard ceiling" at 1.0 of `max_tokens`. Trim
triggers at soft, hard-stop is at hard.

**Risk:** Low. The change is to a calculation, not a control flow.
The user-facing behavior change is: compaction happens earlier.

#### Priority 2 — Per-message-type weighting (OpenCode)

**What:** Add a `weight` field to `ChatMessage` (or a static lookup
in `models/conversation.py`) that classifies messages as `system`,
`user`, `assistant`, or `tool_result`, and a `protected_types` set
in the trim policy.

**Why:** OpenCode's `PRUNE_PROTECTED_TOOLS` and the protected
"skill" message list show that different message types have
different *evictability* profiles. Trimming a tool result is
lossy but recoverable (the agent can re-read the file). Trimming
the system prompt is catastrophic.

**Where:** `models/conversation.py:trim_to_token_limit` (line 365).
The function currently treats all messages equally.

**Risk:** Low. The change is to message accounting, not message
order. Existing tests should pass.

#### Priority 3 — `keep_first` invariant (OpenHands)

**What:** Add a `keep_first: int = 2` to the trim policy. The
first 2 messages (system + first user) are never trimmed, even
if the budget would demand it.

**Why:** OpenHands' `keep_first` is the only invariant that
prevents the agent from losing its own identity. This is
non-obvious to implementers but critical for correctness.

**Where:** `models/conversation.py:trim_to_token_limit` (line 365).
Add a `policy.keep_first` parameter and short-circuit the trim if
it would touch those messages.

**Risk:** Low. The change is defensive — it only constrains the
trim, never loosens it.

#### Priority 4 — Head/tail split with role anchoring (Aider)

**What:** When `tail_preserve` is exhausted and the trim still
doesn't fit, switch to a "head/tail" mode: summarize the head
into one message, keep the tail verbatim, glue them together
with the head summary on top.

**Why:** Aider's role-anchoring (`while messages[split_index - 1]
["role"] != "assistant"`) prevents the LLM from being asked to
"continue" a conversation that ends on a user turn. This is a
correctness fix that crabcakes' current trim doesn't make.

**Where:** `models/conversation.py:trim_to_token_limit` (line 365)
+ `summarize_oldest_user_messages()` (line 460). The two functions
need to coordinate: trim picks the split point, summary produces
the head.

**Risk:** Medium. This changes the structure of the message
list after trim. CB-6 (tool message orphaning) needs to be
considered here — if the head summary drops a tool result, the
subsequent tool call message may be orphaned.

#### Priority 5 — `hard_context_reset` fallback (OpenHands)

**What:** When `summarize_oldest_user_messages()` returns a
summary that itself exceeds the budget, retry with progressively
smaller event sizes (OpenHands uses `* 0.8` per attempt, 5
retries).

**Why:** Pathological conversations (one giant tool result) can
otherwise fail the summary, leaving the user stuck. The fallback
gives *some* summary instead of a hard failure.

**Where:** `models/conversation.py:summarize_oldest_user_messages`
(line 460). Add a `max_retries` parameter and a
`context_scaling: float = 0.8` field.

**Risk:** Low. The fallback is bounded (max 5 retries) and only
triggers on failure.

#### Priority 6 — Async summarization (Aider)

**What:** Move `summarize_oldest_user_messages()` to a background
thread, with a barrier that the next LLM call waits on.

**Why:** Aider's async summarization doesn't block the main loop.
The user can keep typing while the summary is generated. The
next LLM call uses the compressed form.

**Where:** `agent/runtime.py:process_turn` (the main loop) and
`models/conversation.py:summarize_oldest_user_messages`. This
requires plumbing a `threading.Event` or `concurrent.futures.Future`
between the two.

**Risk:** High. This is the most invasive change — it affects
the runtime's threading model. Defer until priorities 1-5 are
shipped and stable.

#### Priority 7 — Pluggable condenser (OpenHands, deferred)

**What:** Define a `ContextCondenser` protocol so users can plug
in custom strategies (e.g., "always keep the last 5 user
messages, no summary").

**Why:** OpenHands' pluggable design is the right end-state, but
it's overkill for a 1.0 release. crabcakes has a single concrete
strategy; let users request alternatives before building the
abstraction.

**Where:** `models/conversation.py` (define the protocol) +
`agent/runtime.py` (use the configured strategy).

**Risk:** Low. The protocol is additive; existing callers can
ignore it.

### 7.3 What to explicitly *not* copy

| From | Pattern | Why not |
|---|---|---|
| Claude Code | Summary injected as a user turn | Loses the ability to distinguish "real" user turns from summary turns. crabcakes already has the `is_summary` flag (line 124 of `models/conversation.py`); preserve it |
| Aider | PageRank-based repo map | Out of scope for context management. The repo map is a prompt-enrichment feature, not a context-management one |
| Cline | Per-model token windows doc page | Useful, but a docs task, not a code task |
| OpenCode | Hardcoded `PRUNE_PROTECT = 40_000` constant | Issue #21208 documents the bug. Make it config-driven from day one |

### 7.4 Cross-cutting concerns

#### 7.4.1 The pairing invariant (CB-6)

The pairing invariant — every `tool` message's `tool_call_id` must
appear in some `assistant` message's `tool_calls[].id` — interacts
with every priority above. Any trim that removes an `assistant`
message with `tool_calls` must also remove the corresponding
`tool` messages, or the LLM will reject the request.

`trim_to_token_limit` already handles this (it walks backwards and
preserves the pairing). The proposed changes must not break this
invariant. The pairing invariant is the single most important
correctness property of the trim function.

#### 7.4.2 The `is_summary` flag

`ChatMessage.is_summary: bool = False` (line 124) is a
crabcakes-specific feature that none of the surveyed projects
have. It marks a message as "this is a summary produced by
`summarize_oldest_user_messages`, not a real conversation
turn." This is the right abstraction. The proposed changes
should preserve it (i.e., the head/tail split should produce a
summary message with `is_summary=True`).

#### 7.4.3 The `default_max_tokens` field (SPEC-MODEL-CAPACITY-DISCOVERY)

The companion spec `SPEC-MODEL-CAPACITY-DISCOVERY.md` adds a
`default_max_tokens: int = 0` field to `ProviderConfig`, which
the Test Connection flow populates from the OpenAI-compatible
`/v1/models` endpoint. This is the *input* to all the trigger
percentage work above. The two specs are complementary:
`SPEC-MODEL-CAPACITY-DISCOVERY` is the *discovery* step,
this report is the *policy* step.

### 7.5 A worked example

For a 200k-context conversation in crabcakes (after the proposed
changes):

1. **Turn 1-10** run normally. `usage = 5k of 200k = 2.5%`. No
   trigger.

2. **Turn 11-50** build up. `usage = 80k of 200k = 40%`. Still
   no trigger (0.80 threshold).

3. **Turn 51** has a `read` tool result of 100k tokens. `usage =
   180k of 200k = 90%`. The 0.80 trigger fires.

4. **Step 1 of compaction:** OpenCode-style `prune()`. The
   `read` tool result is marked compacted (2k char stub). New
   `usage = 82k of 200k = 41%`. Trigger is satisfied.

5. **Step 2 of compaction** (would run if step 1 didn't free
   enough): Aider-style head/tail split. The head is summarized
   into one `is_summary=True` message, the tail is kept verbatim.
   The pairing invariant is preserved (we never split an
   `assistant` message from its `tool_calls`).

6. **Step 3 of compaction** (fallback if step 2 produces an
   oversized summary): OpenHands-style `hard_context_reset`.
   Retry with progressively smaller events until the summary
   fits.

7. **The next LLM call** uses the compacted message list. The
   user sees "compaction happened, freed 98k tokens" in the
   UI.

### 7.6 Metrics to track

When this design ships, measure:

| Metric | Why | Target |
|---|---|---|
| API cost per task | Headline win from the OpenHands benchmark | -30% to -50% |
| Tokens per LLM call | Direct measure of context reduction | 50% reduction at 80% trigger |
| Time to first response after a `read` of a large file | UX win from tool-output awareness | <2s |
| Number of `context_length_exceeded` errors per 100 turns | Reliability | 0 |
| Number of `tool_call_id` pairing violations per 100 turns | Correctness | 0 (already enforced) |
| User-visible "context used" percentage | UX transparency | Always shown in the conversation UI |

## 9. Open Questions for Future Research

1. **What does Anthropic's own Claude API recommend for context
   management?** The public docs are thin. Worth investigating
   once their published best-practices doc is more detailed.

2. **Does Aider's repo map actually pay for itself?** Aider
   claims it does, but the empirical evidence is anecdotal. A
   controlled experiment (with vs. without repo map, same
   benchmark) would settle it.

3. **What's the right `keep_first` number?** OpenHands defaults
   to 2 (system + first user). Is that right for crabcakes, or
   should the first *assistant* turn also be kept? The first
   assistant turn often contains the agent's plan, which is
   high-value to preserve.

4. **What's the right default trigger percentage?** 0.80 is
   Cline's default and the consensus, but crabcakes' user
   population (developers working on long-running tasks in a
   single window) might prefer 0.75. Worth a user-facing
   configurable default.

5. **Should the trim be opt-in or opt-out?** Currently it's
   implicit (the model loop calls trim before sending). If a
   user wants the model to *fail loudly* when over-budget
   (for debugging), the trim should be toggleable. This is
   a small UX feature but a real one.
