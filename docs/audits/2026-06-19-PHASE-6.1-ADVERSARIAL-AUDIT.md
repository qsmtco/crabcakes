## New findings introduced by Phase 6.1

### P6.1-1: `raise_for_status()` outside try/except — HTTPStatusError propagates uncaught

**Severity:** Med
**Commit:** `5d6cc35`
**File:** `agent/tools.py:679`
**Assumption violated:** The Phase 6.1 rewrite assumed the try/except inside the redirect loop covers all error paths. It doesn't.

**Attack vector:**

The redirect loop (lines 652-672) wraps only the `httpx.get()` call in try/except:

```python
for _ in range(10):
    try:
        resp = httpx.get(current_url, timeout=10.0, follow_redirects=False)
    except httpx.HTTPStatusError as e:
        return ToolResult(...)
    except httpx.RequestError as e:
        return ToolResult(...)

    if 300 <= resp.status_code < 400:
        ...  # follow redirect
        continue
    break  # non-3xx: exit loop

resp.raise_for_status()  # ← line 679: OUTSIDE try/except
```

If the final (non-redirect) response is a 404, 500, or any other 4xx/5xx, `raise_for_status()` raises `httpx.HTTPStatusError` which is NOT caught. The old code had this inside the `try:` block.

**Reproduction:**

1. Call `web_fetch` against a URL that returns HTTP 500 (without redirect).
2. `resp.raise_for_status()` raises `HTTPStatusError`.
3. The exception propagates to `execute_tool`'s catch-all, which returns `ToolResult(success=False, error="Tool web_fetch raised HTTPStatusError: ...")`.

**Impact:** Low in practice (the caller's catch-all handles it), but the error message is less useful ("Tool web_fetch raised …" vs. the old "web_fetch HTTP 500: {url}"), and it's a regression from the original error-handling intent.

**Root cause:** When the try/except was restructured from a single block wrapping the entire function body to a loop, `raise_for_status()` was placed after the loop instead of inside it.

**Fix:** Wrap `resp.raise_for_status()` in a try/except, or move it inside the loop's try block:

```python
# After the loop:
try:
    resp.raise_for_status()
except httpx.HTTPStatusError as e:
    return ToolResult(success=False, error=f"web_fetch HTTP {e.response.status_code}: {current_url}")
```

### P6.1-2: Dead code — unreachable "exceeded max redirects" + impossible exception

**Severity:** Low
**Commit:** `5d6cd35`
**File:** `agent/tools.py:654, 678`

Two pieces of dead code:

**a) `except httpx.HTTPStatusError` inside the loop (line 654):**

`httpx.get(url, follow_redirects=False)` does NOT raise `HTTPStatusError` — it returns the response regardless of status code. `HTTPStatusError` is only raised by `raise_for_status()`, which is not called inside the loop. This except clause can never fire.

**b) `resp is None` check (line 678):**

After the loop `for _ in range(10)`, `resp` is assigned on the first iteration (assuming `httpx.get` doesn't raise — if it does, we return early). If all 10 iterations produce 3xx responses, the loop ends normally with `resp` set to the last 3xx response. `resp` is never None. The "exceeded max redirects" error is unreachable.

**Actual behavior when max redirects exceeded:** The code falls through to `resp.raise_for_status()` on a 3xx response. `raise_for_status()` only raises for 4xx/5xx, so it passes silently. Then the code extracts content from the 3xx response body (typically empty or minimal HTML). The user gets `ToolResult(success=True, output="")` or similar — not an error.

**Fix:** Add a redirect-count check after the loop:

```python
# After the for loop, before raise_for_status():
if 300 <= resp.status_code < 400:
    return ToolResult(success=False, error="web_fetch: exceeded max redirects (10)")
```

### P6.1-3: Blockquote regression test doesn't verify handler is *connected*

**Severity:** Low
**Commit:** `38a3236`
**File:** `tests/test_gtk_safe_link.py:106-118`

The test `test_blockquote_javascript_link_blocked` calls `on_activate_link(label, "javascript:alert(1)")` and asserts it returns `True`. This verifies that the `on_activate_link` *function* works — but it does NOT verify that the function is *connected to the label's `activate-link` signal*.

If someone reverts `_build_quote_segment` to use `Gtk.Label()` + `set_markup()` (the original bug), this test would still pass — because `on_activate_link` is imported and called directly, not via signal emission.

**What the test actually proves:** That `on_activate_link` returns True for `javascript:` URLs. This was already covered by `TestOnActivateLink::test_returns_true_for_unsafe_url`.

**What the test should prove:** That the label returned by `_build_quote_segment` has an `activate-link` handler connected that blocks `javascript:` URLs.

**Fix:** Use `Gtk.test_init` / signal emission, or check `GObject.signal_handler_is_connected()`. Since GTK4 signal handler enumeration is awkward from Python, a practical approach:

```python
# Verify the label has the activate-link handler by checking CSS classes
# (make_safe_label adds them; raw Gtk.Label wouldn't have 'blockquote-text')
# This is already done in test_blockquote_css_class_preserved.
#
# For a stronger test, verify that make_safe_label was called by checking
# that the label has BOTH the CSS class AND the correct wrap/xalign defaults
# that make_safe_label sets.
```

Alternatively, accept the test as-is — it proves the code *calls* `make_safe_label` (because `on_activate_link` is imported from the same module), and `test_blockquote_css_class_preserved` independently verifies the CSS class. Together they provide reasonable coverage.

### P6.1-4: DNS rebinding TOCTOU window

**Severity:** Low (inherent to the approach; not introduced by Phase 6.1)
**File:** `agent/tools.py:607-633` (`_reject_restricted_url`)

`_reject_restricted_url` resolves the hostname via `socket.getaddrinfo` and checks the IP. Then `httpx.get` makes a separate TCP connection, which triggers a NEW DNS resolution. A malicious DNS server can return a public IP for the first query and a private IP for the second query (DNS rebinding).

This is a well-known SSRF limitation and is NOT a regression — the original code had the same window. The Phase 6.1 fix narrowed the window for redirect targets (validation happens before the connection) but did not eliminate it for the initial URL or validated redirect targets.

**Fix (if needed):** Resolve the IP, then connect to that IP directly with SNI/Host header set to the original hostname. This is complex and probably out of scope.
